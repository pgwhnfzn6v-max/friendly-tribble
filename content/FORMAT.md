# 記事＝台本 兼用フォーマット

記事を書いてから台本に直す、という二度手間をなくすための構成規則。
**記事の各ブロックが、そのまま動画の1カットに対応する**ように書く。

## 全体構造

```
├─ フック          記事の冒頭2行 ＝ 動画の最初の5秒
├─ 前提            誰の・どの案件の話か（1段落）
├─ 本編 3〜5ブロック  各ブロック = 動画1カット
│    ├─ 見出し（体言止め・15字以内）
│    ├─ 本文（300〜600字／読み上げて40〜80秒）
│    └─ 【画面】この間に映すもの
├─ 結論            持ち帰り1つに絞る
└─ 導線            PR表記＋リンク1本
```

## ブロックの書き方

### 見出し
体言止め、15字以内。**動画ではそのままテロップになる**ので、長いと画面に入らない。

- ✅ 「実測9個から数量7式へ」
- ❌ 「現地調査で測定した9つの実測値をもとに7つの数量計算式を組み立てた方法について」

### 本文
1ブロック300〜600字。声に出して読むと40〜80秒になる分量。

守ること：
- **一文を短く。** 読み上げるので、句点で息が継げる長さにする。60字を超えたら切る。
- **数字は口に出せる形で。** 「19.5m」はよいが「19,500mm」は読みにくい。記事では正確な単位、動画では読みやすい単位を選ぶ。
- **専門語は初出で1行の説明を足す。** 同業者だけでなく発注者側も読むため。

### 【画面】
ブロックの末尾に必ず1行入れる。撮影・編集時の指示になる。

```
【画面】数量根拠シートの実測値エリア（青字9行）をゆっくりスクロール
```

これがあるので、撮影時に台本を読み直す必要がない。

## ショート台本（55〜70秒）

記事の要約ではなく、**本編ブロックのうち一番驚きがある1つだけ**を切り出す。全体をまとめると必ず薄くなる。

```
0-3秒    フック（結論か、意外な事実を先に言い切る）
3-12秒   前提（何の現場か、10秒以内）
12-45秒  本編（1ポイントのみ。数字を1つ画面に出す）
45-60秒  持ち帰り＋次の一言
```

冒頭3秒で「これは自分の話だ」と思わせられなければ、残り57秒は再生されない。
**現場写真を最初のカットに置く**のが最も効く。図やテロップから始めない。

## SNS投稿文

| 媒体 | 分量 | 書き方 |
|---|---|---|
| X | 140字前後 | 数字を1つ入れる。リンクは末尾。連投しない |
| Instagram | 冒頭2行が勝負 | 写真1枚目に結論のテロップ。本文は改行を多めに |

## 命名規則

`articles/NN-slug-in-english.md`

`NN` は通し番号、`slug` は英小文字とハイフン。日本語ファイル名は使わない（URL とスクリプト処理で扱いづらいため）。

## frontmatter

各記事の先頭に置く。パイプライン側がここを読んで公開処理をする。

```yaml
---
title: 記事タイトル
slug: estimate-from-field-notes
date: 2026-09-05
status: draft        # draft | review | published
source: estimate-sinwa-canopy.xlsx   # 素材になった実案件（匿名化必須）
keywords: [解体 見積, 積算 AI, 建設業 生成AI]
cta: 建設業向け見積SaaS
pr: true             # アフィリエイトリンクを含むか
checked:             # 公開前チェック（README.md 参照）
  anonymized: false
  amounts: false
  legal: false
  numbers: false
  pr_label: false
  no_fake_experience: false
---
```

`status: published` にできるのは `checked` が全て `true` になってからとする。
この6項目が、自動化パイプラインで人が唯一手を動かす箇所になる。
